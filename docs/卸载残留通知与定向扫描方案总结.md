# 卸载残留通知与定向扫描方案总结

> 本文档记录 2026-10 实现的「自动检测卸载残留」功能全貌（对应设置项 `uninstall.autoDetectResidual`），
> 供后续开发、排障与接续工作参考。
>
> 当前状态：代码已全部落地，`cargo check` / `cargo test --lib` / `tsc` / `pnpm build` 全绿；
> **系统通知本体与点击回调仅能在 build .app 产物中验证**，真机手动验收清单（第 8 节）尚未跑完。

---

## 1. 功能概述

设置项：`设置 → 通用 → 自动检测卸载残留`（settings.json 键 `uninstall.autoDetectResidual`，缺失时缺省**开**）。

目标链路（对标腾讯柠檬）：

```
app 拖进废纸篓 → 5s 内检测（residual_watch 常驻轮询）
  → macOS 原生系统通知「检测到应用已卸载」
  → 用户点击 → 应用激活 + 主窗恢复 → 跳转卸载页 orphans tab
  → 自动定向扫描该 app 的残留 → 勾选清理
```

### 交付语义（双通道）

| 通道 | 触发条件 | 用户表现 |
|------|---------|---------|
| **主通道：系统通知** | .app 运行 + 通知授权就绪 | 系统通知横幅；点击 → 主窗恢复 + 跳卸载页 + 定向扫描 |
| **兜底：事件 → 提示条** | dev 模式 / 未授权 / 首次待授权 / 投递失败 | 卸载页内提示条「检测到…」，点「扫描残留」走同一定向链路 |
| **完全静默** | 设置项关闭 | 通知与事件都不发（后端读开关静默 + 前端同时不挂监听，双保险） |

---

## 2. 背景：改造前的负资产状态（为什么要做）

旧实现「骨架真实但触达率近零」，属信任问题而非缺功能：

1. **四条件同时成立才触达**：进程活着 + 开关开 + 用户当时停留在卸载页 + app 在废纸篓停留 ≥5s；
2. **后端完全不读开关**（假开关）：`start_residual_watch` 无条件启动，"设置里承诺自动"与实际行为无关；
3. **事件监听是页面级的**：`uninstall::residual-detected` 只在 `Uninstall/index.tsx` 挂载时监听，不在卸载页时事件静默丢弃且不补报；
4. **payload 只有 appName**，点「扫描残留」仅切 tab 不自动扫描；判重按文件名（同名 app 漏报）。

## 3. 关键设计决策（ADR）

| 决策 | 结论 | 理由 / 被拒备选 |
|------|------|----------------|
| 送达通道 | **objc2 + UNUserNotificationCenter + delegate 点击回调**（自研，不引插件） | 官方 `tauri-plugin-notification` 桌面端**无任何点击回调能力**（源码级证实）；toast 渲染在隐藏窗口用户看不见（主窗 hide 到托盘）；托盘气泡 `request_show` 有连带唤起主窗的已知坑；项目已有非打扰浮窗管线 `macos_reminder_window`（trash_watch 在用），但系统通知更标准、可被系统设置统一管理、支持「应用退出后点击通知中心条目冷启动拉起」 |
| 数据流 | **后端 pending 快照 + take 命令**，事件仅作到达信号 | 对齐 trash_watch「快照是事实源，事件仅通知」原则；规避事件丢失/时序竞态 |
| 定向口径 | **后端严格定向**（bundleId 优先、appName≥3 字符兜底），不做前端过滤 | bundleId 解析本就为通知回跳所需，边际成本低；前端过滤无法解决"点错入口" |
| 开关语义 | **关 = 完全静默**（通知与事件都不发） | 修掉假开关；开关关闭时 `seen` 照常更新，防切换后积压补发 |
| 判重 key | 文件名 → **`文件名\|bundleId`** | 同名不同源不误判 |
| dev 防护 | `current_exe()` 含 `.app/Contents/MacOS/` 才启用原生调用 | 裸二进制调 UNUserNotificationCenter 会失败；dev 下走事件兜底保留可测路径 |
| 本地通知可行性 | 无需 $99 Developer 账号 | 本地通知仅需合法 .app bundle + bundle identifier + ad-hoc 签名 + 用户授权；$99 管的是 Developer ID 签名/公证/MAS/APNs 远程推送 |

## 4. 架构与数据流

```
┌─ residual_watch（常驻线程，5s 轮询 ~/.Trash）──────────────────────────┐
│  启动种子：首轮前收集已有 .app 填充 seen（防误报）                        │
│  每轮：collect_trash_apps → read Info.plist 取 bundleId                  │
│        key = "文件名|bundleId"（判重）                                   │
│        → notify_new_app：读 settings.json（开关/语言）                    │
│           ├─ 开关关 → 静默 return                                        │
│           └─ send_residual_notification（macOS 原生）                     │
│                ├─ 返回 true（已投递）→ 不发事件（避免双通道打扰）           │
│                └─ 返回 false（dev/未授权/首次/失败）→ emit 兜底事件        │
└────────────────────────────────────────────────────────────────────────┘
          │ 系统通知被点击                     │ 兜底事件
          ▼                                   ▼
┌─ delegate didReceive（macos_notifications）┐  ┌─ 卸载页提示条（页面级）─┐
│ 1. set_pending(ResidualTarget) 快照         │  │ 用户点「扫描残留」      │
│ 2. run_on_main_thread(restore_main_window)  │  │ → setResidualTarget    │
│ 3. emit EVT_RESIDUAL_OPEN（到达信号）        │  └────────┬───────────────┘
└────────────────┬───────────────────────────┘           │
                 ▼                                       │
┌─ layout/ResidualContext（Shell 常驻层）─────────────────┴───────────────┐
│ consumePending：invoke take_pending → 有值 → setTarget + navigate       │
│ 冷启动兜底：挂载时 take 一次；运行期：listen EVT_RESIDUAL_OPEN          │
└────────────────┬───────────────────────────────────────────────────────┘
                 ▼
┌─ Uninstall/index.tsx ── residualTarget 非空 → setActiveTab('orphans') ──┐
└────────────────┬───────────────────────────────────────────────────────┘
                 ▼
┌─ OrphansTab ── residualTarget 变化 → runScan(target) ──────────────────┐
│ runScan：mole_orphan_scan_for({bundle_id, app_name})（定向）            │
│       或 mole_orphan_scan()（全量，target 为 null）                     │
│ UI：banner「仅显示"XX"的残留」+「查看全部」按钮（clearResidualTarget）   │
└────────────────────────────────────────────────────────────────────────┘
```

| 命令 | 签名 | 说明 |

### 6.2 事件

| 事件名 | Payload | 语义 |
|--------|---------|------|
| `uninstall::residual-detected` | `{appName, bundleId}` | 兜底通道：通知不可用时触发，卸载页提示条承接 |
| `uninstall::residual-open` | `{appName, bundleId}` | 通知点击**到达信号**；数据仍以 pending 快照为准（take 失败才用 payload 兜底） |

### 6.3 数据结构（前后端对齐，serde camelCase）

```typescript
interface ResidualTarget {
  appName: string           // 进入废纸篓的 .app 名称（不含 .app 后缀）
  bundleId: string | null   // Info.plist 解析失败为 null
  detectedAt: number        // Unix 秒
}
interface ResidualDetectedPayload { appName: string; bundleId: string | null }
```

通知 `userInfo` 键：`appName` / `bundleId`（NSString，仅这两键，与 delegate 回调读取端约定一致）。

## 7. 行为细节与不变量（改代码前必读）

1. **delegate 必须强持有**：`UNUserNotificationCenter.delegate` 是 weak 属性，`static DELEGATE: OnceLock<Retained<...>>` 不持有则回调静默失效；
2. **`install_early` 必须在 `run()` 开头（Builder 之前）**：覆盖「应用未运行 → 点击通知冷启动」场景，晚注册错过本次点击回调；
3. **快照是事实源，事件仅到达信号**：点击回调先落 pending 再 emit；前端 take 失败才用事件 payload 兜底（时间戳现场生成）；
4. **take 命令不能被 Batcher 合并**：并发合并会让第二次调用拿到第一次的结果，吞掉新 pending——已在 `useTauri.ts` bypass；
5. **pending 单槽**：新请求覆盖旧请求（Mutex<Option>）；
6. **授权弹框时机**：首次检测到新 app 时发起（有上下文）；本次通知必走兜底（返回 false）；`AUTH_REQUESTED` 防重弹；`AUTH_STATE` 拒绝后 send 直接返回 false；
7. **开关双读**：后端不读 → 假开关；前端不读 → 关开关后提示条仍泄露打扰语义。两处都要；
8. **`seen` 无论开关与否都更新**：防开关切换后的积压补发；
9. **定向匹配口径**：归一化（小写 + 去 ` -_ .`）后 `contains`；bundleId 非空 → 仅 bundleId 匹配；为空 → appName 归一化长度 ≥3 才参与（短名误报面过大）；安全策略（`ORPHAN_SKIP_PREFIXES`、高风险 dotpath、deletable 规则）与全量扫描共用、不因定向放宽；
10. **点击回调线程无保证**：窗口恢复统一 `app.run_on_main_thread(restore_main_window)`；
11. **通知投递结果短等 5s**：`add` 的 completion 正常毫秒级返回；超时按成功处理，避免"通知已发出但兜底事件也触发"的双通道打扰；
12. **通知 identifier = `mole.residual.{appName}`**：立即投递（trigger=nil），无判重需求。

## 9. 排障手册（症状 → 排查路径）

**环境事实**：
- 运行日志：`~/Library/Logs/com.tiyong.molan/molan.log`
  ⚠️ **日志按构建分级：debug 构建 Debug 级，release 构建降为 Warn** —— `[residual_watch]` / `[notifications]` 的 info 日志在 release 版不落盘，排障请用 debug 构建；
- 设置文件：`~/Library/Application Support/com.tiyong.molan/settings.json`（顶层拆 key；`uninstall.autoDetectResidual` 缺失 = 缺省开）。

### 9.1 拖 app 进废纸篓完全没反应

1. 应用是否在运行（托盘驻留）？检测依赖常驻线程（`start_residual_watch`，setup 阶段启动）；
2. 设置开关是否开？（设置页 + settings.json 双确认）；
3. app 是否在废纸篓停留 ≥5s？（轮询粒度，秒级延迟正常）；
4. 日志查 `[residual_watch] new .app detected`；
5. dev 模式？→ 预期行为是走兜底，需在卸载页看提示条。

### 9.2 有提示条但没有系统通知

预期场景（按优先级核对）：
- dev 模式（无 bundle）→ 设计如此；
- 未授权 / 首次待授权 → 检查「系统设置 → 通知 → Molan」；
- 日志查 `[notifications] native delegate installed`、`authorization requested`、`add request failed`。

### 9.3 点通知没有跳转

1. 日志查 `[notifications] residual notification clicked`——有 → 后端链路 OK，查前端；
2. 前端：layout 是否挂载（ResidualProvider 在 Shell 常驻层）；take 命令是否被 Batcher 合并（历史坑，已 bypass）；
3. pending 被抢先消费？take 是消费语义，若无其他消费方（目前仅 layout 一处）不应发生。

### 9.4 点击通知冷启动不跳转（唯一不确定点）

- 根因域：delegate 注册时序 vs 系统投递点击回调的先后（delegate 已最大化提前到 `run()` 开头）；
- 备选方案：注入 `NSApplicationDelegate` 的 `applicationDidFinishLaunching`（参考 `macos_dock_quit.rs` 的 ObjC 注入先例）。

### 9.5 定向扫描结果全量 / 为空 / 匹配错误

1. 日志查 `[orphan_scan] targeted scan (bundleId=..., name=...) hit N entr(ies)`；
2. bundleId 解析失败（Info.plist 缺失/异常）→ 回落 appName 匹配，且归一化长度 <3 时不匹配任何项（定向空态「未发现"XX"的残留文件」+ 查看全部入口是预期 UI）；
3. 前端状态：banner 是否显示（`residualTarget` 非空即定向态）；
4. 匹配口径见第 7 节第 9 条。

### 9.6 关开关后仍收到通知（不应发生）

1. 确认写入确实落到 `~/Library/Application Support/com.tiyong.molan/settings.json`（前端 store 与后端读取同文件）；
2. 时序：改开关后立即拖 app——前端持久化是异步的，稍候即可；
3. 后端读取逻辑 `auto_detect_enabled`（缺失/损坏缺省 true）——若文件里是 `false` 而仍打扰，查读取路径是否偏移（identifier 变更等）。

### 9.7 同名 app 漏报 / 误报

判重 key = `文件名|bundleId`：同名不同源不误判；同名同源正常判重。若 bundleId 解析失败（落 `文件名|`），退化为旧的文件名语义。

## 10. 已知限制与风险

1. **通知本体仅能在 build .app 验证**：dev 走事件兜底，不崩但无通知；
2. **冷启动点击时序**（唯一不确定点）：见 9.4，备选方案已备；
3. **`AUTH_STATE` 是启动时快照**：用户中途在系统设置里改权限（尤其 Denied → 允许），需**重启应用**才刷新；Authorized → Denied 中途变更则表现为 send 失败 → 兜底事件；
4. **首次授权弹框出现时本次通知必走兜底**（设计如此，有上下文才弹框）；
5. **release 构建 info 级日志不落盘**：排障需 debug 构建；
6. **P2 离线补报未做**（明确押后）：应用退出期间进入废纸篓的 app 无感知；未来若做，口径应为「只补偿上次退出之后进入废纸篓、且至今未被清倒的 app」；
7. **定向兜底门槛**：bundleId 解析失败且 appName 归一化 <3 字符时不参与定向匹配（防短名误报）；
8. **不引入 tauri-plugin-notification**（桌面端无点击回调，硬限制）；**MAS 沙箱版短期不做**，通知 API 在沙箱下的适配未验证。

## 假设与边界
