# 第三方更新执行引擎设计方案

> 目标：让 Molan 在应用内完成对第三方 App（Sparkle 2 源，如 iTerm2）的完整更新——下载、验证、安装、重启，全程纯 Rust 实现。
> 对标：Burrow（Swift + 内嵌 Sparkle 框架）。**等价功能、零第三方更新框架**。
> 状态：待评审（评审通过后按 §10 里程碑实施）。

---

## 1. 范围

### P0（本设计实施范围）
- **Sparkle 2 源 + zip 全量包**更新（覆盖 iTerm2 及多数主流独立 App）
- 完整安全验证链（见 §4）
- 安装前置条件：目标 App 位于**用户可写路径**（用户自装 App 的默认情况）
- 两步确认交互：下载前确认 → 验证后「安装并重启」

### 明确不做（防范围蔓延）
- ❌ Sparkle 1.x（DSA 老签名）→ 回退现有「打开应用」交接
- ❌ delta 增量更新（用全量包）
- ❌ dmg 格式更新包（P1）
- ❌ Electron generic 源（P1）
- ❌ 提权安装（目标 App 不可写时的 AEWP 安装，P1）→ P0 明确报错提示手动更新
- ❌ App Store 应用（系统限制，维持打开 App Store）

### P1/P2 预留
- P1：dmg 挂载安装、Electron generic、AEWP 提权安装
- P2：delta、批量更新、回滚 UI

## 3. 架构与模块

```
lib/updates/engine/            ← 新模块（更新执行引擎）
├── mod.rs            引擎入口：任务编排 + 引擎级单例（防并发）
├── feed.rs           appcast 完整条目解析（扩展 appcast.rs）
├── download.rs       下载（https-only、512MB 上限、进度事件、可取消）
├── staging.rs        安全暂存目录（mkdtemp + 0700 + 原子操作 + 路径固定）
├── verify/
│   ├── mod.rs        验证链编排（五道门顺序执行）
│   ├── eddsa.rs      Ed25519 验签（ed25519-dalek；纯 Rust）
│   └── codesign.rs   SecStaticCode FFI（Apple 锚定 + 身份信息提取）
├── identity.rs       BundleIdentity 快照 / 比对 / 一致性规则
├── installer.rs      退出目标 App → 备份 → 原子替换 → 复验 → 回滚
└── relaunch.rs       目标 App 退出等待 + 重启（NSRunningApplication FFI）
```

**分层约定**（沿用 `lib/updates` 现有约定）：
- `engine/` 只放纯逻辑 + 系统 API 调用；Tauri command 薄层在 `controllers/updates.rs` 扩展
- 事件常量与 payload 定义在 `crate::events`
- 前端契约常量登记在 `src/constants/tauri-commands.ts` / `tauri-events.ts`

## 4. 安全验证链（核心）

> **铁律：任何一道门失败 → 丢弃暂存、不触碰系统文件、报告失败。绝不降级安装。**

| 门 | 验证内容 | 依据 | 失败后果 |
|---|---|---|---|
| 1 来源验证 | appcast enclosure 的 `sparkle:edSignature` 对更新包文件的 Ed25519 验签 | 目标 App Info.plist 的 `SUPublicEDKey` | 丢弃 |
| 2 下载防护 | https-only；重定向降级拒绝；大小 ≤512MB；下载中断/不满校验 | 协议实现 | 丢弃 |
| 3 暂存安全 | `mkdtemp` 随机目录；`chmod 0700`；后续操作全部基于已固定路径（防路径竞态） | 对齐 Burrow 纪律 | 丢弃 |
| 4 落地验证 | 解压出的新 `.app` bundle：`SecStaticCodeCheckValidity` + requirement `anchor apple generic`（全架构检查） | macOS Security.framework | 丢弃 |
| 5 身份一致性 | 新 bundle 与旧 bundle 比对：bundleId / signingIdentifier / teamIdentifier 必须一致；替换后**再复验一次**（含 cdhash 防调包） | 对齐 Burrow `BundleUpdateIdentity` | 丢弃 / 回滚 |

补充规则：
- `/System/` 下的任何路径直接拒绝（SIP 保护 + 系统 App）
- 目标 App 不可写 → P0 明确报错（"请在应用内或手动更新"），不做提权安装
- 目标 App 未持有 `SUPublicEDKey`（Sparkle 1.x 特征）→ 明确不支持，回退交接

## 5. 状态机与前后端契约

**流程状态机**（Burrow `UpdatePhase` 的 P0 子集）：

```
idle → downloading(percent) → verifying → readyToInstall → installing → completed
                                    ↘ failed(reason)     ↘ cancelled
```

**Tauri 契约（新增）**：

| 类型 | 名称 | 说明 |
|---|---|---|
| 命令 | `mole_updates_install` | `{ app_path }`：解析 feed → 下载 → 验证 → 暂存就绪（异步，进度走事件）；返回新版本号摘要 |
| 命令 | `mole_updates_install_commit` | `{ app_path }`：退出目标 App → 替换 → 复验 → 重启（失败自动回滚） |
| 命令 | `mole_updates_install_cancel` | `{ app_path }`：丢弃暂存 |
| 事件 | `updates::install-progress` | `{ app_path, stage, percent?, message? }` |
| 前端常量 | `EVT_UPDATES_INSTALL_PROGRESS` / `CMD_MOLE_UPDATES_INSTALL*` | 按现有常量文件登记 |

**前端交互（UpdatesTab）**：
- 点击「更新」（sparkle 源且可更新）→ 确认对话框（版本对比摘要）→ 确认后按钮变行内进度（百分比）
- 验证通过 → 按钮变「**安装并重启**」
- 安装中 → 行内进度（"正在替换…"）
- 完成 → 行内绿勾「已更新到 vX」
- 失败 → 行内红字 + 失败原因（保留「重试」）
- P0 排除场景（Sparkle 1.x / dmg / 不可写）→ 维持现有「打开应用」交接

## 6. 关键边界与防护清单

- **运行中目标 App**：`install_commit` 先发 terminate 请求，≤8s 等待；未退出则中止（不做任何系统改动）
- **并发**：引擎单例——同一时刻仅一个安装任务；同一 App 的重复请求去重
- **超时**：下载 15 分钟上限；`SecStaticCode` 验证在 `spawn_blocking` 中执行并设 60s 软超时（已知 trustd 偶发慢）
- **取消**：下载阶段可取消；进入 installing 原子段后不可取消
- **暂存清理**：取消/失败即时清理；进程启动时清理遗留暂存目录（前缀识别 + 归属校验）
- **日志**：阶段/路径/校验结果摘要进 debug 日志；**不记录签名原文**

## 8. 测试计划

- **单元测试**：appcast 完整条目解析（含真实离线 fixture）；EdDSA 正/反例（篡改 1 字节必须拒绝）；identity 比对规则；Zip Slip 样本拒绝
- **FFI 对照测试**：`codesign.rs` 提取的 identity 与 `codesign -dv` 命令行输出对照一致
- **真机集成（手动，验收清单）**：iTerm2 全流程正例；篡改包反例；运行中未退出取消例；中途失败回滚例
- **回归**：现有「打开应用」交接路径在 P0 排除场景下行为不变

## 9. 评审决策点

1. **确认交互**：两步确认（下载前 + 安装重启前），对齐 Sparkle 语义 —— 是否认可？
2. **P0 边界**：不做提权安装（不可写时明确报错走手动）—— 是否认可？
3. **运行中 App**：安装前强制请求退出，未退出则中止 —— 是否认可？
4. **依赖**：新增 `ed25519-dalek` / `zip` 两个 crate（成熟活跃、MIT/BSD）—— 是否认可？
5. **失败哲学**：任何验证失败绝不降级安装（宁可失败交回手动）—— 是否认可？
