# 清空废纸篓功能方案总结

> 状态：代码已实施，编译、构建与 21 项定向测试全部通过；**真机交互尚未验证**（确认框呈现、实际清空效果、卡片淡出时序），见第九节。
> 关联功能：废纸篓超阈值提醒（右上角浮窗）。提醒的开关与阈值在本目录「通用」分组配置；清空动作在提醒浮窗上，不在设置页。
> 落位说明：按用户要求放在 `src/pages/Settings/`（同目录已有 `SETTINGS_ROADMAP.md` 先例）；跨模块架构规范类文档按项目约定应放 `docs/`。

---

## 一、背景：为什么要做这个

### 1.1 旧链路的语义矛盾（本次改造的直接动因）

旧实现中，提醒浮窗主按钮是「去清理」→ 打开主窗 → 跳转 Clean 页自动扫描。存在三个问题：

| 问题 | 说明 |
|---|---|
| **语义错位** | 提醒说"废纸篓垃圾已超过 X"，但 Clean 页扫的是系统/应用缓存，**根本不碰 `~/.Trash`**——用户清完缓存，废纸篓一点没小 |
| **死胡同** | Clean 执行被 `CLEAN_EXECUTION_BLOCKED` 硬拦截（旧删除链路未合规），用户从提醒跳过去会看到扫描结果但「立即清理」按钮被禁用，且无从得知原因 |
| **门禁矛盾** | 提醒的意图是"引导用户执行清理"，门禁却统一禁止所有执行路径——引导与阻断互相打架 |

### 1.2 一个绕不开的物理事实

**清空废纸篓 = 永久删除。** 废纸篓里的文件已经在 `~/.Trash` 内，不可能"再次移入废纸篓"来释放空间；唯一的手段就是把它们永久删除（参考腾讯柠檬 `LMTrashSizeCheckWindowController` 的 `cleanAction` 即对 `~/.Trash/*` 逐项 `removeItemAtPath`）。这决定了本功能与红线的关系，见第三节。

## 二、方案取舍（含被否决的路径）

| 候选方案 | 结论 | 否决/采纳理由 |
|---|---|---|
| 按**导航来源**放行 Clean 门禁（提醒来源→允许执行） | ❌ 否决 | 来源由前端自报不可信；即使可信，提醒用户点的「立即清理」走的仍是同一段含 `rm -rf` 回退的删除代码——"同一操作对提醒安全、对 Home 危险"在逻辑上不成立 |
| **模式门控**解锁 Clean 的"移到废纸篓"模式 | ❌ 否决 | 前置条件是移除 `safe_remove_ex` 里 trash 失败后回退 `rm -rf` 的分支——这会触碰红线敏感的删除原语和已验收的清理链路（明确约束：不动） |
| 提醒改「查看」→ 打开 Finder 废纸篓 | 备选未采纳 | 语义最干净（不碰红线），但失去应用内闭环；保留为未来 MAS 沙箱受限时的退路 |
| **独立"清空废纸篓"能力**（最终方案） | ✅ 采纳 | 与 Clean 缓存清理链路**完全隔离**、零触碰；语义对齐柠檬；真正解决用户"释放废纸篓空间"的诉求 |

## 三、红线边界决策（用户拍板）

| 红线 | 关系 | 说明 |
|---|---|---|
| 红线1：禁外部二进制/Shell | ✅ 不违反 | 删除用原生 `std::fs::remove_file` / `remove_dir_all`（系统调用级），**不调用 `Command::new("rm")`** |
| 红线4：清理走 trash crate、不直接 rm | ⚠️ **字面冲突，记录在案的例外** | 清空废纸篓本质就是永久删除，逻辑上无法满足"走 trash"。例外成立的边界：仅作用于用户自己已丢弃的 `~/.Trash`、不接受任何路径参数、强制二次确认 |
| 红线5：高危能力走用户确认 | ✅ 满足 | 清空前经 `moleNativeConfirm` 弹原生 NSAlert 警告级确认，明确"此操作不可恢复" |

隔离原则：本能力与 Clean 缓存清理链路及其 `CLEAN_EXECUTION_BLOCKED` 门禁**互不影响**；旧删除链路的整改状态不因本功能改变。

## 四、架构与实现

### 4.1 后端：`src-tauri/src/trash_empty.rs`（新模块）

`empty_trash() -> Result<EmptyTrashResult, String>`，设计要点：

| 要点 | 实现 |
|---|---|
| **路径零信任** | 服务端硬编码 `dirs::home_dir()/.Trash`，**不接受任何前端路径参数**，杜绝被诱导删到别处 |
| **二次校验** | `symlink_metadata` 确认目标为真实目录且非符号链接，否则返回 `TRASH_UNAVAILABLE` |
| **删除策略** | 真实目录 → `remove_dir_all`（Rust 实现不跟随内部符号链接）；文件/**符号链接** → `remove_file`（断链，绝不递归进链接目标） |
| **统计口径** | `deleted`（成功顶层条目数）/ `failed`（失败数，单条失败不中断整体）/ `reclaimedBytes`（成功条目逻辑字节累加，符号链接只计链接自身大小） |
| **稳定错误码** | `TRASH_HOME_UNAVAILABLE` / `TRASH_UNAVAILABLE` / `TRASH_UNREADABLE` |
| **线程模型** | 命令层 `spawn_blocking` 执行，重 I/O 不阻塞 |

### 4.2 后端：命令与提醒状态联动

- `mole_trash_empty`（`controllers/settings.rs`）：`require_window` **仅允许 `trash-reminder` 窗口调用**；成功后调用提醒服务 `on_trash_emptied()`。
- `trash_watch.rs` 新增 `on_trash_emptied()`：走 `invalidate()`（epoch++、置 Hidden、清 reminderId/error、dirty 标记、revision++）→ 发布 Hidden 快照 → 卡片淡出；同时唤醒 watcher 重新基线化。**诚实性**：清空成功后废纸篓必低于阈值，立即隐藏不构成虚假反馈。

### 4.3 前端：`TrashReminderWindow/index.tsx`

- 主按钮 `emptyTrash` 流程：`moleNativeConfirm`（warning）二次确认 → 确认后 `invoke(CMD_MOLE_TRASH_EMPTY)` → `failed > 0` 时保留卡片并提示"部分项目未能清空，请重试"，否则随 Hidden 快照淡出。
- **操作序号守卫**（`operation.current` token）：确认框挂起期间若到达新提醒快照（reminderId 变化），旧操作全部失效，不会把结果误写到新提醒上；取消确认则无任何副作用。
- 清空进行中按钮显示「清理中」并禁用（前端本地 `pending` 态，未新增后端阶段）。

### 4.4 文案（i18n，对齐柠檬）

| key | 文案 | 变化 |
|---|---|---|
| `trashReminder.title` | 是否清空废纸篓？ | 原"是否前往清理？" |
| `trashReminder.capacity` | 废纸篓垃圾已超过 | 原"已达到" |
| `trashReminder.empty` / `emptying` / `cancel` | 清空 / 清理中 / 取消 | 新增（替代 open/opening） |
| `trashReminder.emptyConfirmTitle` / `emptyConfirmBody` | 确定清空废纸篓？/ 此操作不可恢复，废纸篓内所有项目将被永久删除。 | 新增 |
| `trashReminder.emptyPartialFailed` / `emptyFailed` | 部分项目未能清空，请重试 / 清空失败，请重试 | 新增（替代 openFailed） |

## 五、交互流程

```text
浮窗「是否清空废纸篓？废纸篓垃圾已超过 X」
  ├─ 暂不清理 / Esc → 写自然日暂缓（次日零点）→ 淡出隐藏
  └─ 清空 → 原生确认框「确定清空废纸篓？此操作不可恢复…」[取消] [清空]
        ├─ 取消 / Esc → 回到浮窗，无副作用
        └─ 清空 → 按钮「清理中」禁用 → mole_trash_empty（spawn_blocking）
              ├─ 全部成功 → 后端 on_trash_emptied 发布 Hidden → 卡片淡出
              └─ 有失败   → 卡片保留，提示「部分项目未能清空，请重试」可重试
              └─ 调用失败 → 卡片保留，按错误码映射文案（readFailed/emptyFailed）
```

## 九、未验证项（需真机）

- **确认框呈现**：`moleNativeConfirm` 在浮窗可见时会以 sheet 挂到 344×144 的小卡片上，观感是否可接受未实测（不可见时回退 app-modal 居中）。
- **实际清空效果**：`deleted/failed/reclaimedBytes` 在真实废纸篓（含目录、符号链接、权限异常条目）上的准确性。
- **隐藏时序**：`on_trash_emptied` 的立即 Hidden 与 kqueue 目录事件触发的重测两条路径叠加后，卡片淡出是否稳定。
- **MAS 沙箱**：沙箱版对 `~/.Trash` 的访问需书签/授权，full 版无此问题；未验证。
- 真机验证建议：**先用少量可弃测试文件验证**，确认后再处理真实数据——清空是永久删除，二次确认是唯一防误触屏障。
